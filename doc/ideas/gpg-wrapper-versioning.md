The gpg-passphrase-wrapper that bin/setup writes on every repo has no single
source of truth — it's regenerated inline by a heredoc, and a stale hand-edited
copy on a persistent volume silently broke commit signing.

# gpg-passphrase-wrapper — version it, stop regenerating inline

## incident (2026-07-24)

Signing failed during SE-2887 work with:

```
gpg: no valid OpenPGP data found.
gpg: processing message failed: Unknown system error
```

`git config --get gpg.program` pointed at `/usr/local/bin/gpg-passphrase-wrapper`,
which doesn't exist in this container. The only copy present was at
`/root/bin/gpg-passphrase-wrapper` (a persistent volume, survives across
sessions), and its contents were broken:

```bash
#!/usr/bin/env bash
_gpg_passphrase=8ocVuWuor+
exec gpg --batch --passphrase  --pinentry-mode loopback 
```

The passphrase was hardcoded literally (instead of resolved from
`$GPG_PASSPHRASE`/`/run/secrets/gpg_passphrase`), `--passphrase` had nothing
after it, and `"$@"` was dropped entirely — so no signing args ever reached
`gpg`.

## root cause

The canonical template, written inline by every repo's `bin/setup`
(`commit_signing()` function, generated by an external script per each repo's
`AGENTS.md` header) is correct:

```bash
cat >/usr/local/bin/gpg-passphrase-wrapper <<'WRAPPER'
#!/usr/bin/env bash
_gpg_passphrase="${GPG_PASSPHRASE:-$(cat /run/secrets/gpg_passphrase 2>/dev/null)}"
exec gpg --batch --passphrase "${_gpg_passphrase}" --pinentry-mode loopback "$@"
WRAPPER
chmod +x /usr/local/bin/gpg-passphrase-wrapper
git config --global gpg.program /usr/local/bin/gpg-passphrase-wrapper
```

Quoted heredoc (`<<'WRAPPER'`), lazy variable resolution, `"$@"` passthrough —
all correct. But this heredoc only ever writes to `/usr/local/bin`, a path that
doesn't persist and doesn't exist in every container flavor. At some point an
agent session, working in an environment where `/usr/local/bin` wasn't usable
or didn't exist, manually flattened/inlined the resolved passphrase into a
copy at `/root/bin` (a path that *is* persistent) to unblock itself — losing
the quoting and `"$@"` in the process. That broken copy then silently shadowed
the correct template on every subsequent session that happened to source
`/root/bin` first in `$PATH`, or where `bin/setup` didn't rerun to overwrite it.

No file tracks "this is the wrapper, this is its one correct version" — it's
generated ad hoc, in place, by every single repo's setup script, with no
diffing, no review, and no way to notice drift until a signature silently
fails.

## proposal

1. **Commit the canonical wrapper to `interface/bin/gpg-passphrase-wrapper`.**
   Reviewable, diffable, single source of truth.
2. **`bin/setup`'s `commit_signing()` fetches it instead of writing a heredoc:**
   ```bash
   curl -fsSL https://raw.githubusercontent.com/rthomazel/interface/dev/bin/gpg-passphrase-wrapper \
     -o /usr/local/bin/gpg-passphrase-wrapper \
     && chmod +x /usr/local/bin/gpg-passphrase-wrapper \
     || { echo "bin/setup: WARN could not fetch gpg-passphrase-wrapper, writing fallback" >&2; <inline heredoc fallback>; }
   ```
   `interface` is public, so this avoids requiring a clone or credentials — a
   plain unauthenticated `curl` against the raw GitHub URL works.
3. **Keep an inline heredoc fallback** for when `curl`/network is unavailable —
   this is also the version an agent should reproduce by hand if both curl and
   the fallback path fail. Document the exact script contents in the `github`
   skill (or a new small skill) so an agent troubleshooting a broken wrapper
   has the correct reference to recreate it manually instead of improvising.
4. **Never hand-edit the deployed wrapper.** If it's broken, re-fetch or
   regenerate from the documented source — don't patch the flattened copy in
   place, which is what caused the drift.
